# Incremental synchronization

The application opens its local database and reads the active account's controls before it schedules network work. A request can begin only for a selected repository whose verified credential generation still matches the installed credential. Sign-out, Work offline and switching accounts invalidate in-flight claims. Pausing background refresh leaves explicit reads eligible. Queued-action pause and notification quiet mode are independent settings.

## Time zones

Threadline stores instants as milliseconds since the Unix epoch in UTC. GitHub timestamps with explicit offsets identify the same instant after normalization. Request cursors and HTTP validators retain their protocol representation. Date labels use the selected IANA time zone and show its abbreviation and numeric UTC offset, including during the repeated hour when daylight saving ends. The Updated since filter includes the start of the entered local date. Updated before excludes the start of its entered local date. Both bounds are converted to UTC before querying SQLite.

The user preference is UTF-8 text in `display-timezone` under the platform's Threadline configuration directory. A missing file or `system` follows the operating system zone, with UTC as a fallback if its zone cannot be resolved. An isolated test profile uses its own `Config/display-timezone` and defaults to UTC. The configuration file is independent of account credentials and cached content.

## Timing and admission

The default work window is Monday through Friday from 09:00 to 17:00 in the user’s effective time zone. Work hours and quiet hours each accept an independent IANA override. The scheduler tests each UTC instant against the named zone's local weekday and time, including overnight windows. The default intervals are 120 seconds during work, 30 minutes otherwise and 60 seconds for a visible item. The application uses a monotonic clock for elapsed waits. SQLite stores UTC deadlines and completed progress across restarts. [Time-zone conversion](https://docs.rs/chrono-tz/0.10.4/chrono_tz/) · [System time-zone lookup](https://docs.rs/iana-time-zone/0.1.65/iana_time_zone/fn.get_timezone.html)

Each subscription names its account, repository, optional item, resource family and revision. Two panes showing the same revision share a request. Unsubscribing the final owner invalidates the claim. A claim admits one read page. The weighted rotation grants turns to explicit reads, visible items, activity, recent items and reconciliation even under sustained high-priority demand. At most two requests are active per account, and claims are spaced by at least one second. A later server budget can extend this hold. A missed timer produces one due job for its resource. Each completed read schedules its next interval from the current check.

Transient reads receive up to four automatic retries after delays of 5, 15, 30 and 60 seconds, extended by the shared server floor. Repeated failure holds the job for a new explicit request. An interrupted read may reclaim its lease after 90 seconds. A credential failure holds progress until authorization has been repaired or explicitly retried. The queue's mutation eligibility remains a separate read-only signal for the future dispatcher. [Read scheduling](../../crates/threadline-storage/src/sync.rs)

## Change observations

Repository issue and ordinary-comment streams each keep their own successful watermark, five-minute overlap, pagination cursor, first-page validators and baseline. Both streams can observe unopened items. The first request starts with a recent overlap. The issue request includes closed items, and a changed ordinary comment comes from its own update feed. The storage transaction commits downloaded facts, matching activity and page progress together. A partial SSO page can publish returned facts while retaining the input cursor and holding further requests. An expired cursor restarts the affected overlapping window. Conditional validators apply only to their original first-page query.

An event key includes its provider object ID, category and trustworthy source time. The journal recognizes a newly created comment separately from a later edit. Old records can establish state without generating activity. Known state changes on a previously observed issue are recorded even when higher issue numbers are already cached. The repository feed can update downloaded discussions and their active refreshes without marking an unopened discussion complete.
